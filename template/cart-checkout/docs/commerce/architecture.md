# Commerce flow

The cart core is shared by existing product pages and the optional PDP. It persists SKU/path/selection-specific lines per store view, and sends only order-item fields to the API. Shipping rates and totals are calculated by the Commerce API, not the browser subtotal.

Standard checkout: shipping estimate → preview → create with estimate token → PayPal redirect → server return to review → confirm → verified `payment_completed` complete. Express from cart: PayPal session → address/option PATCH → preview of the default/selected option → payer lookup → order creation from the *same* preview payload → initiate `paypal-express` → review → confirm → verified complete. Cart mutations between preview and creation abort the flow. Cancellations and pending states preserve the cart; after verified completion the cart is cleared only if it still matches the order's saved cart snapshot, so a new cross-tab addition is not discarded. A tab-scoped order ID + email is used only to look up the API order, never as success proof. Checkout form fields (including address) are kept in tab-scoped session storage so a PayPal cancellation can restore the form; they are cleared after a verified completed payment. Express also checkpoints the PayPal session ID and previewed shipping/cart snapshot in tab-scoped storage so the SDK's return callback can resume after a mobile redirect; that checkpoint is removed after review handoff or buyer cancellation. Adjust this behavior to the merchant's privacy policy.

The PayPal SDK adapter stays in `scripts/commerce/payments/`; merchant-specific product data, address validation, strings, and checkout presentation can be customized independently. This is a starter, not a payment certification. Complete sandbox and browser accessibility/integration testing in the customer storefront before production.
